# «Копия»: движки раздельно, совет — общий · 23.08.2026

Решение владельца: три стратегии — **«Копия»**, **«Дуэт»**, **«Создание»** — живут
порознь, у каждой свои движки. Общее между ними только одно: **ИИ-центр**,
который советует движок по разборам, а человек всегда может выбрать иной.
Этот документ — про «Копию»: что чинилось, что заведено и как устроено.

## 1. Почему «Копия» не работала 21–23.08

Не из-за моделей. Edge-функция `creator-generate` при приёмке результата читала
MP4 в память целиком — части, склейка, тело загрузки в Storage: 3–4 копии
файла в одном изоляте. 5-секундный Kling (11 МБ) проходил, 12-секундный
(31,5 МБ) — `Memory limit exceeded`, HTTP 546, по одному падению на каждый
опрос воркера (359 за сутки). Наряд `f7318ae3` ($2.04) двое суток висел в
`processing` с нулём опросов и запирал лимит «один открытый запуск» —
отсюда «ничего не запускается».

**Чинит** `supabase/functions/_shared/provider-output-archive.ts` —
потоковая приёмка в два прохода (sha256 без буфера → загрузка в Storage
потоком с хешем в метаданных, которые сверяет база). Тест с настоящим HTTP:
48 МБ → рост памяти < 16 МБ. Выложено в прод как **v673** (хотфикс поверх v672,
без незакоммиченной стройки «Дуэта»). Наряд дошёл до архива на первом же
опросе. Подробности и приём деплоя без CI — в памяти проекта
(`contentengine-edge-memory-crash-streaming`).

## 2. Что такое движок

Движок = **строка реестра** `content_factory.generation_strategy_provider_routes`.
Она называет модель (`model_key`), провайдера, цену и способ счёта
(`price_kind`, `price_rate_minor`, `pricing_version`), окно длительности, кто
задаёт длительность (`duration_source`), уровни качества и — с 23.08 — два
новых свойства:

| свойство | что говорит |
|---|---|
| `engine_family` | `edit` — правит объект в готовом кадре; `regenerate` — собирает ролик заново по референсу; `overlay` — накладывает поверх нетронутого ролика («Дуэт») |
| `input_profile` | что движок принимает: окно длительности и размеры видео, сколько фото и как они называются в указании (`region` / `at_refs` / `named_refs`), сохраняется ли звук исходника. Форма проверяется `generation_strategy_input_profile_valid` |

Код касается движка ровно в трёх словарях — и **нигде больше**:

1. `_shared/generation-strategy-catalog.js` — имя модели (единственный литерал
   в коде), форма тела (`FAL_STRATEGY_MODEL_SHAPES`), версия прайса.
2. `_shared/generation-strategy-edge-contract.js` — исполнимый маршрут
   (`PROVIDER_POLICY_ROUTES`), адреса очереди выводятся из него.
3. `_shared/generation-recipe-adapters.js` — сборщик тела по форме
   (`buildFalProductSwapBody`) и указание (`falProductSwapInstruction`).

Плюс словарь версий прайса в базе (CHECK двух таблиц) и в портале
(`generation-strategy-runtime.js`, `app.js`) — тест
`tests/test_generation_copy_engines_v1.py` следит, что все слои совпадают.

**Версия прайса у каждого движка своя.** Пара `(provider, pricing_version)`
среди включённых строк — подпись маршрута (индекс `…_signature_key`), по ней
опрос восстанавливает модель оплаченной задачи. Два движка fal с одной версией
были бы неразличимы.

## 4. ИИ-центр: совет по движку

`web/app/generation-engine-advisor.js` — чистый модуль без DOM и сети.
Вход: строки реестра + факты запуска (длительность исходника, измеренная
сервером; короткая сторона, если известна; число отмеченных фото; категория;
замысел/разбор; потолок бюджета). Выход: один движок с причинами, два
запасных, отсеянные с причинами.

Правила, по убыванию веса:

1. Окно длительности и размер исходника, бюджет — **отсев**, не штраф.
2. Редакторы (`edit`) впереди пересборщиков всегда, пока хоть один подходит.
3. Крупный товар (категория/замысел: мангал, мебель, техника…) или ≥3 фото →
   нужны движки с несколькими ракурсами (`images.max ≥ 4`); одно фото
   небольшого товара → Pika.
4. Премиальный уровень — никогда по умолчанию.
5. Дешевле — лучше при прочих равных.

Экран (`generation-strategy-intake-v4.js`, каскад «Модель»): **явный выбор
человека → совет ИИ-центра → отметка реестра → первый включённый.** Выбор,
сделанный не человеком, а прошлым советом, не закрепляется: изменились факты
(загрузили ещё фото, выбрали другой исходник) — изменится совет. Подпись под
каскадом всегда называет отдельно «советует» и «исполнит», плюс «отсеяно».
Советчик грузится лениво: без него экран работает по отметке реестра.

Что пока не знает советчик: размер исходника в пикселях (серверная проверка
MP4 измеряет только длительность) и потолок бюджета кампании. Оба поля уже
есть во входе — подключаются, когда появятся источники.

## 7. Вторая половина дня 23.08: «Создание», «Дуэт», выкладка

### «Создание» — четыре движка (миграция `202608230021`)

Ролик-референс провайдеру не уходит (роли каталога), поэтому движки — класс
«фото товара + описание → видео», все `regenerate`, длительность и кадр выбирает
оператор, только 720p:

| движок | цена | вход |
|---|---|---|
| **MiniMax H3** `minimax/h3/reference-to-video` — по умолчанию | 6¢/с (768P) | до 5 фото (Image 1…), 5–15 с |
| Grok Imagine `xai/grok-imagine-video/reference-to-video` | 8¢/с (720p) | до 5 фото (@Image1…), 4–10 с |
| Happy Horse `alibaba/happy-horse/reference-to-video` | 14¢/с (720p) | до 5 фото (character1…), 4–15 с, фото ≥400px |
| Seedance 2.5 `bytedance/seedance-2.5/reference-to-video` | 48¢/с (720p, без видео-референса) | до 6 фото, 4–15 с, premium |

Несуществующий рецептный адрес Runway `/v1/recipes/product_ad` убран из
списка исполнимых пар. Цена маршрута (`generation_strategy_route_price` и
`…_recipe_price`) теперь отвергает разрешение, которого нет в `quality_modes`
строки: 1080p-кадр для 720p-движка — отказ, а не молчаливая цена. Форма
«Создания» прячет кадры, которых выбранный движок не делает, и перерисовывает
их при смене движка. Советчик ИИ-центра работает и для «Создания» (по числу
фото, категории, замыслу и выбранной длительности).

**Что чинилось попутно:** нормализатор ассетов (`generation-strategy-assets.js`)
валил ВСЮ страницу ассетов, встретив пару (стратегия, роль), которой не знал
(старая роль «Аватара» от сервера без миграций «Дуэта») — «Создание» оставалось
без исходников. Теперь незнакомые роли отбрасываются по одной.

**Требование «ровно 10 MP4» у «Создания» оставлено как есть** — это продуктовое
решение (один ролик на каждый референс). Снизить до 1..10 можно отдельным
заходом.

### «Дуэт» — сборка у провайдера (миграция `202608230022`)

Прежний замысел «прозрачный WebM + наш ffmpeg» не имел хоста (edge ffmpeg не
запускает, сервера приложения в проде нет). Теперь HeyGen v2
`POST /v2/video/generate` получает исходник **фоном** (подписанная ссылка) и
ставит ведущего поверх кружком (`talking_photo_style: circle`) или вырезом
(`matting`) в указанном углу (`scale`/`offset` из раскладки ведущего);
результат — MP4, который принимает потоковый приём. Опрос: `GET /v3/videos/{id}`,
при отказе `GET /v1/video_status.get`. Маршрут включён и рекомендован, рубильник
знает `heygen:avatar_v3`, `duet_presenter_id` доезжает до привязки.

Ведущий регистрируется из формы: кнопка «Показать личности и голоса» читает
каталог кабинета HeyGen через edge (`duet_presenter_catalog`; ключ в браузер
не уходит), оператор выбирает фото-аватар/видеоаватар и голос, даёт имя →
`creator_register_duet_presenter`. Фото/описание аватара из формы убраны;
текст брифа — **речь ведущего** (он произнесёт её вслух).

Ограничения: длина дуэта = длина речи (короче ролика — обрежется, длиннее —
последний кадр замрёт: `play_style: freeze`); коэффициенты `scale`/`offset`
выведены из документации и калибруются первым прогоном
(`heygenOverlayPlacement` в адаптере); v1/v2 HeyGen живут до 31.10.2026 — далее
HyperFrames. **Сверка повисшего HeyGen-наряда не реализована** (коды
подтверждения знают только RUNWAY/FAL) — если первый дуэт повиснет, закрывать
SQL-ом. Ключ `HEYGEN_API_KEY` в Supabase должен завести владелец.

## 8. Вечер 23.08: вкладка висла при выборе MP4 (commit 403de34)

Симптом у владельца на зеркале прода: выбрал MP4 в «Копии» — форма повисла,
процессор на 100 %. Воспроизведено локально и поймано новым зондом
`scripts/browser_hang_probe.py` (логин → маршрут → `DOM.setFileInputFiles` →
восемь `Debugger.pause` подряд с печатью кадров стека, синтетических
input/change, планировщиков rAF и мутаций DOM; вердикт BUSY/IDLE).

Две петли, кормившие друг друга:

1. **Один слот состояния каскада на три панели.** `state.copyEngine`
   перезаписывался рендером каждой панели; «Дуэт» рисовался последним и
   оставлял `heygen:…`, память экспресс-панели запоминала его как движок
   «Копии» и при каждом монтировании писала в общее поле
   `generation_intake_engine`; «Копия» своего движка там не находила, ставила
   свой → change → монтирование → … Теперь состояние пострaтегийное
   (`cascadeStateFor` / `storeCascadeState`, `state.engineCascades`),
   обработчики радиокнопок пишут в слот той панели, где случилось событие, а
   радиокнопки «Дуэта» носят суффикс `__avatar_video` — иначе браузер держал бы
   одну отметку на обе панели (обработчики и paid-lock в app.js ловят имя по
   префиксу `name^=`).
2. **Безусловная перестройка `<select>` ведущего и товара «Дуэта».** Рабочий
   стол перемонтирует адаптеры на любую childList-мутацию, а каждое
   перемонтирование рождало `replaceChildren()` → мутацию → следующее
   перемонтирование. Теперь `syncSelectOptions` перестраивает список только при
   смене набора вариантов, а раскладка ведущего подставляется при смене
   ведущего, а не на каждой перерисовке (иначе угол/форма, выставленные под
   ролик, откатывались бы сами).

Регресс-тест `test_copy_panel_survives_mp4_selection_without_remount_ping_pong`;
проба загрузки в `browser_smoke.py` доходит до «MP4 выбран · 8.1 с из допустимых
15 с». Штамп сборки `20260823.copy-engines.64`, чтобы браузер не взял
закэшированные модули `.39`.

**Правило для адаптеров рабочего стола:** любая запись в DOM при монтировании
обязана быть идемпотентной (отпечаток → пропуск), иначе наблюдатель
`workspace-os-v4.js` превращает её в вечное перемонтирование. Проверка — зонд
зависания, а не глаз.

## 9. Вечер 23.08: «Дуэт» доведён до серверной проверки (commit 77a768a)

Прогон `scripts/browser_duet_flow_probe.py` с файлом владельца показал, что
после «Подготовить аватара» дуэт не проходил ни один слой. Починено:

**Браузер.** Экспресс-машина «Копии» (бесплатные шаги мастера → серверная
цена → «Запустить за $X») стала общей: маршрут берётся из активной панели
(`expressRoute`), «Дуэт» получил кампанию, двухфазную кнопку «Подготовить
дуэт» и остаётся в компактном виде вместо полного конструктора. Свежий MP4
объявлялся пригодным только «Копии» (оверлей guided) — «Выбрано 0 из 1».
app.js сверял проекцию с литералом `viral_product_swap`. Дуэту нужен разбор
ролика (202608220006) — панель получила карточку «Разбор ролика для речи
ведущего» (поля общие с нативным редактором), товар уходит в ТЗ явным
`product_id`, audio=false. Речь ведущего ограничена длиной ролика (≈15
знаков/с, ≤1500 — правило `generation_strategy_prompt_snapshot`): счётчик
показывает предел, кнопка отказывает раньше сервера. `MAX_AVATAR_DURATION` 60.

**Сервер (`202608230023_duet_prepare_scope_fixes_v1`, прод применён).**
Пять расхождений контракта: `reference_video` true у product_ugc в подготовке
против false у валидатора/зеркала; разбор механики не читался в ветке правки
видео; ворота проекта и версия ТЗ знали целью только фото товара (исходник
дуэта привязывается к названному товару, вид `source_video` допущен);
триггер подписи привязки исключал исходник дуэта из реестра, который binder
туда кладёт. pgTAP `generation_strategy_duet_prepare_scope_fixes_v1_test.sql`.

**Edge (`creator-generate` v676).** Валидатор снимка цены сравнивал
`ratio "source"` с отсутствующим `selection.ratio` у дуэта → 503 без имени;
`*_prompt_invalid` теперь 422 с именованным сообщением.

Локально дуэт доходит до проверки готовности провайдера (ключа HeyGen на
стенде нет) — та же граница, что у «Копии». Первый прогон в проде калибрует
раскладку ведущего (`heygenOverlayPlacement`).
